# TrustRide security and deployment

This is defense in depth, not a guarantee against every attack. Volumetric DDoS protection belongs at an edge/WAF before traffic reaches Next.js, Redis, Supabase, or OCR workers.

## Application controls

- Prisma model methods and tagged SQL bind values. `npm run security:check` rejects unsafe raw-query APIs and unreviewed raw HTML rendering in application sources. Do not concatenate user text into SQL or bypass this gate.
- Every admin mutation calls `requireAdmin`; role comes from `UserProfile`, never editable Auth metadata. Booking mutations require CLIENT, verified active Auth sessions, and owner-specific booking filters. Private document reads remain owner/admin scoped and use short-lived links. Direct Data API access to application tables is revoked by migrations and RLS is enabled.
- Unsafe HTTP methods require an exact site Origin and reject cross-site Fetch Metadata. Next Server Actions retain their own origin protection. JSON routes read at most 16 KiB even for chunked bodies; Server Actions cap multipart bodies at 22 MiB. An ingress must also enforce body/header/read timeouts.
- New uploads accept JPEG/PNG only, at most 5 MiB and 20 million decoded pixels. Filename extension, declared MIME, magic bytes, decoder format, page count, and full decoding must agree. Re-encoding strips metadata and appended content; random storage paths prevent filename execution/path traversal. PDFs, SVG, executable extensions and malformed images are rejected. Existing PDF records are retained for compatibility. This does not provide malware scanning or prove the identity shown in an image.
- Nonce-based script CSP blocks unapproved scripts; production excludes JavaScript `unsafe-eval`. Inline styles remain necessary for current UI/animation. Remote images/connections are allowed for existing media integrations. Narrow these origins when the final asset-host list is known.
- Responses include no-sniff, no-frame, referrer, permissions, opener, and production HSTS headers. Private routes use no-store. TLS termination is required.
- Authentication, mutations, reads, OCR and route lookups are limited. OCR already bounds its queue; DB pool size and statement timeouts limit resource usage. Redis counters use an atomic script and expiring hashed keys. Configured Redis failures reject requests with 503 rather than bypass protection. Exhausted budgets return 429 and Retry-After at ingress/API level.

## Required production infrastructure

1. Place the app behind your provider's DDoS protection/WAF. Block direct origin access; all visitors must pass through the ingress. Enable bot challenges and stricter login/upload rules, request/header/body limits, short slow-client timeouts, connection limits, and a 22 MiB upload ceiling. Cache public static assets; never cache personalized responses or signed document links. Protect Next image optimization at the edge too: it is excluded from application Proxy matching.
2. Configure `UPSTASH_REDIS_REST_URL` (HTTPS), `UPSTASH_REDIS_REST_TOKEN`, and `REQUIRE_DISTRIBUTED_RATE_LIMIT=true` in runtime secrets. Use a region near the app. Without Redis and enforcement, the bounded in-process fallback is for development or a single instance only and does not protect multiple replicas. The release workflow refuses this configuration.
3. Set `TRUSTED_PROXY_IP_HEADER` only to a header that your ingress overwrites. For example use an ingress-overwritten `x-real-ip` on a private Nginx origin; use the provider's documented client-IP header on managed hosting. Never trust arbitrary visitor `x-forwarded-for`. Without this setting traffic shares an `unidentified` budget; configure it before production. Do not expose a second path to the origin that can spoof this header.
4. Set `NEXT_PUBLIC_SITE_URL` to the exact canonical HTTPS origin, and redirect alternative hosts at ingress. Client mutations from another origin will be rejected.
5. Use distinct staging/production secrets and data. Runtime DB credentials should have only the privileges the application needs, not ownership/DDL. The current active-session check needs SELECT on `auth.sessions`; grant only that necessary read or expose a reviewed narrowly scoped check. Use a separate session/direct migration connection, never a transaction-pooler port for Prisma migration locks. Set database connection and statement limits at the role as well as the application.
6. In Supabase, keep `booking-requirements` private; never put customer documents in public `vehicle-assets`. Review bucket size/MIME limits, owner/admin storage policies, Auth rate limits, email confirmation, password settings, CAPTCHA, MFA for operators, and budget alerts. Auth and Storage can also be called directly: app request limits cannot protect the Supabase API. Authenticated users currently have owner-folder Storage insert/delete policies; they can upload unreferenced objects directly, but cannot overwrite random saved paths or attach them to another booking. To disable direct uploads entirely, migrate to a dedicated server-only Storage identity and remove direct client insert permissions; provision that identity before changing policies. Do not expose service keys in public env vars.
7. Enable encrypted backups/PITR, error/429/503/latency monitoring, credential rotation, log retention without ID images/tokens, and provider spending limits. Add managed malware scanning/quarantine if required. Keep dependencies patched and review weekly Dependabot PRs.

## CI and release

- `.github/workflows/ci.yml` runs on PRs and main/master pushes: clean install, generated client, static security gate, lint, types, tests, migration tests on local Postgres, production dependency audit, build and smoke checks. CI-only schema stubs emulate just the Supabase objects referenced by migrations; they do not establish live Auth/Storage behavior. No production credentials go to PR jobs.
- `deploy.yml` is a manual release from main/master. It calls the same CI workflow, uses the protected GitHub `production` environment, builds and pushes immutable `ghcr.io/<owner>/<repo>:<commit>` images, applies reviewed migrations, then sends `{ "image": "..." }` to a deployment provider hook. Set environment required reviewers/branch restrictions and branch protection in GitHub. The hook must deploy that exact tag, supply runtime env, perform readiness checks, and keep the previous image for rollback. Configure the hook before running the release; no deployment provider has been connected automatically.
- GitHub environment variables: `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `TRUSTED_PROXY_IP_HEADER`. Secrets: `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`, `MIGRATION_DATABASE_URL`, `DEPLOY_WEBHOOK_URL`, `DEPLOY_WEBHOOK_TOKEN`. Runtime also needs `DATABASE_URL`, these security settings, and existing Mapbox settings. Only public browser configuration is passed to Docker build args. Never put runtime or migration credentials in a Docker build context.
- Migrate using an expand/contract approach; back up first. A rollback deploys the prior image, not destructive reverse SQL. Check backward compatibility of schema changes.
- Existing project database: migration deploy reported P3005 (existing schema without a Prisma migration baseline). The rating column/range constraint , image-only bucket restrictions, and profile-photo schema/policies were applied and verified independently. Before enabling release migrations, compare the actual schema/policies/functions with each checked-in migration, back up, and run `prisma migrate resolve --applied <migration-directory>` ONLY for migrations already fully present. Do not mark historical migrations applied blindly. New empty environments should use `prisma migrate deploy` against an initialized Supabase project normally.
- Run a real staging acceptance check with one admin and two clients: cross-account booking/document access, denied client admin mutations, revoked sessions, valid and disguised uploads, OCR limits, Origin rejection, rating persistence/admin moderation, and distributed rate-limit expiry. Local automated tests do not replace that check.

## Incident response

Use WAF rules to shed abusive traffic, temporarily disable costly OCR if needed, rotate exposed credentials, review ownership/audit records and provider usage, and restore from verified backups when appropriate. Do not log or share customer documents during diagnosis.

Profile-photo storage is a separate public bucket with owner-folder write/delete policies. Only validated, re-encoded files uploaded through Account settings are referenced by user profiles. Signed-in users are redirected home from guest authentication pages, with the same guard on the authentication action. Recovery-session password changes remain accessible.

The Delivered lifecycle enum, constraints, transition guard, and private scheduled advance function were applied and verified on the existing project. The active pg_cron job runs every minute; live run history reported successful execution. Include these changes when reconciling the existing migration baseline. Delivered periods retain exclusion/maintenance protections, and browser database roles cannot call the transition function.
